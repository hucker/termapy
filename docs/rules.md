# Rule registry

The rules the code relies on, one row each, in one place. Until 2026-10-12 they
lived in four: the guards in `tests/test_architecture.py`, the prose bullets in
`CLAUDE.md`, each review's "invariants checked and holding" list, and the
maintainer's head. This table is the registry; those are the pointers. The
decisions behind the rules are in [`decisions.md`](decisions.md). The rows are
rules of every kind: only the `data` rows are invariants in the strict sense,
which is why the file was renamed from `invariants.md` on 2026-10-14.

**Reading a row.** `id` is stable and kebab-case, the name a test's marker
gives (`@pytest.mark.rule("ui-layer-textual")`) and a review cites. `kind` is the column
the table exists for: a **guarantee** is enforced by the named test, so a
violation anywhere fails `pytest`; an **assumption** holds because someone read
the code, and stays true only until someone does not. `category` says what the
statement ranges over, because each category has a different strongest guard:
**data** is a predicate over runtime state or a value's vocabulary (the
invariant in the strict sense; its strongest guard is a constructor or parser
that refuses the bad state), **concurrency** is which thread may do what and
who owns a resource, **structure** is the import graph or the shape of the code
(an `ast` scan), **repository** is two artifacts agreeing at every commit (a
diff test), **contract** is a pre- or postcondition on a handler or a
pipeline stage (what the serial reader promises its consumers, say),
**requirement** is behavior a user sees (a scenario test), and **hygiene** is a
tool's verdict on the whole tree, the gate run as a test. `enforced by` names
a guarantee's guard, the test whose failure means the rule is broken anywhere,
with its probe after a semicolon, and `review` for an assumption; every test
that pins the rule, the guard and each instance, carries the rule's marker and
is listed in the generated [`traceability-matrix.md`](traceability-matrix.md). `source` is
where the rule is stated. `last review check` is the
most recent adversarial pass that read it at the path; guarantees are checked
on every run, so the date there is the last human confirmation only.

**Keeping it honest.** `tests/test_architecture.py::test_rules_registry_matches_the_guards`
reads this table and fails when a row names a test that does not exist, a
guarantee names no test, a guard in that file carries no registered id, or a
test a row names does not carry the row's marker; `tests/conftest.py` refuses
a marker that names no id at collection (the id sources are
`tests/traceability.py`). A new guard therefore cannot ship unlisted, a
renamed test cannot leave a row pointing at nothing, and a tagged test cannot
name a rule nobody wrote down. `uv run pytest --rule <id>` runs the tests of
one rule; [`traceability.md`](traceability.md) is the process. A change that
relies on a rule names its id; a new rule gets a row the same day, an
assumption until its guard exists; a review that finds one broken flips it to
assumption until the fix lands and says so in its Addenda.
