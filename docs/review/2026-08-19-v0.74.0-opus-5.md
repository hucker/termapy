**Scope note:** this is a single-axis pass — thread safety and the efficiency of
the serial data path. It is not a general code-quality review. No hardware was
attached; findings were reproduced against `FakeSerial` and synthetic ports that
reproduce the real timing shape.

**Verdict:** The design is sound and most of it is right — the non-blocking
dispatch lock is deadlock-free by construction, RX batching is already
well-tuned (~0.25 blocking round-trips per KB), and `serial_claimed` cleanly
eliminates reader/transfer port contention. The defects cluster into three
mechanism gaps, not scattered mistakes. One is a genuine data-integrity bug: a
stale reader thread can close the *next* connection's port, leaving the app
believing it is connected when it is not (T1, reproduced). Two shutdown paths
hang the process after the TUI exits (T4, T5). The documented threading model in
`CLAUDE.md` is **inverted** with respect to the implementation (D1), which
matters because it is the stated rationale for a live design decision.

---

## Root cause: unowned handles and unscoped cancellation tokens

The findings below are symptoms of three mechanism gaps. Fixing the mechanisms
retires each *class* of defect.

1. **Shared handles have no owner and no identity check.** `_port_obj`,
   `_serial_port`, `log_fh`, and `CaptureEngine._fh` are each written by one
   thread and read-then-used by another via bare `if x: x.method()`. Nothing
   establishes which thread may close them, and no site re-checks identity
   before acting. This is T1 (the reader closes a handle it never opened), T7,
   and T8. The fix shape is uniform: bind to a local, and let only the opener
   close.

2. **Teardown negotiates with a timeout instead of a join.** `disconnect()`
   waits on `reader_stopped` for `READER_STOP_WAIT_S` and then proceeds
   *regardless*. The documented invariant that makes this safe
   (`SERIAL_READ_TIMEOUT_S << READER_STOP_WAIT_S`) bounds `read()` but not the
   `on_lines` callback, which blocks on the very thread doing the waiting. That
   is T1/T2. A `Thread.join()` has no such hole.

3. **Cancellation tokens are global where the operation is local.**
   `_stop_event` does double duty (stop the reader / cancel the reconnect loop);
   `_script_stop` is one flag that `/repeat` feels entitled to `clear()`;
   `_script_depth` is one counter for what can be two concurrent scripts. That
   is T3, T4, T6, and D3. Each operation needs its own token.

## The threading model as built (not as documented)

Recording this because `CLAUDE.md` currently describes a different system (D1).

| Role | Entry point | Marshalling to main |
|---|---|---|
| Serial reader | `@work(thread=True) app._run_reader` → `SerialEngine.read_loop` | callbacks via blocking `call_from_thread` |
| Command dispatch | `@work(thread=True) app._dispatch_on_thread*` — **every** typed command, button, and palette entry | none; output helpers self-marshal |
| Script runner | `@work(thread=True) app._run_script` → `repl.run_script` | none; `_dispatch_single` runs **inline** on that thread |
| Main | Textual event loop | — |

Nothing dispatches commands to the main thread. Instead each output helper
(`_status`, `_set_status_bar`, `_write_output_markup`, `_on_main`) compares
`self._thread_id` and forwards itself. Concurrency across dispatchers is bounded
by `_dispatch_guard`, a **non-blocking** `RLock`. The governing rule is stated
correctly at `app.py:2756-2757`: *"every user command goes through a
`@work(thread=True)` method so blocking handlers never freeze the TUI."*

### T1 — reproduction

The failing interleaving requires only that RX be in flight across a
disconnect/reconnect that happens in one main-thread turn (config switch, port
picker, `/cfg baudrate`). Orchestrator repro against the real `SerialEngine`
with `on_lines` blocking exactly as `call_from_thread` does:

```
gen1 reader parked in on_lines : True
main-thread stall              : 0.61s (2x0.3s)
NEW port open after connect    : True

NEW port is_open               : False
NEW port closed_by             : reader-gen1
engine._port_obj               : None
engine.is_connected            : False
```

Sequence: the reader parks in `call_from_thread`; the main thread enters
`reader_stopped.wait(0.3)` and can no longer service the callback, so the wait
is *certain* to expire; `disconnect()` closes the old port; `connect()` opens the
new one and **clears both events**, disarming the stale loop's stop check; the
event loop finally runs, the old reader resumes, breaks on its stale local
`port.is_open`, and its `finally` closes `self._port_obj` — now the new port.

Observable result: the port the user just selected is dead immediately after the
"Connected: COMx" banner, and `ctx.serial.*` silently no-ops because every host
helper is guarded by `if self.engine.serial_port:`. The spurious
`_reader_stopped.set()` also disarms the gate for the *next* connect.

`tests/test_serial_engine.py` `TestTeardownContract` pins
`SERIAL_READ_TIMEOUT_S * 3 <= READER_STOP_WAIT_S` and cannot catch this: the
delay lives in the callback, not in `read()`.

## Design issues (D)

| # | Grade | Finding |
|---|---|---|
| D1 | **Verified** | **The documented threading model is inverted.** `CLAUDE.md` states *"Script commands are dispatched to the main thread via `call_from_thread`"*, and `repl.py:1661-1663` repeats it. Both are false: `_dispatch_single` calls `repl.dispatch_full` inline (`app.py:2839`), and `_run_line` calls `sctx.dispatch_fn(stripped)` directly (`repl.py:1692`). Nothing marshals. This matters because it is the stated rationale for `_BLOCKING_COMMANDS` — anyone reasoning from the documented model will add or omit entries for the wrong reason. Probable drift from the pre-`355b5ea` design. |
| D2 | **Assessment** | **Backpressure is "block the reader."** The reader's only response to a slow main thread is to stall inside `call_from_thread` behind a 4096-byte read cap, so it can never catch up after a stall. This is also what makes T1/T2 reachable — a stalled main thread breaks teardown. Basis: `on_lines` is the sole RX→UI path and `call_from_thread` blocks on `future.result()` (textual `app.py:1834-1838`). Worth evaluating `post_message` for `on_lines`. |
| D3 | **Verified** | **`_dispatch_guard` converts contention into silent data loss.** Non-blocking is the right call for deadlock-freedom, but the loser receives `CmdResult.fail("Busy - a command is still running.")` and the line is **skipped, not delayed**. Under T6, `/repeat count=3 cmd=/run slow.run` was measured dropping 6 lines. On a serial tool a skipped line means a command that never reached the device. |
| D4 | **Verified** | `_thread_id` is a **private Textual attribute** (`App.__init__` / `_thread_init`), read in four places in `app.py`. It works in 8.2.7, and Textual's post-shutdown `_thread_id = 0` is harmless because `call_from_thread`'s `_loop is None` check fires first. Still an unpinned dependency on an internal; capturing an own id in `on_mount` costs two lines. |

## Efficiency findings (E)

The reader path is well built. Every cost below sits *inside* the blocking
round-trip, on the main thread, while the reader is stalled — so main-thread
work is RX throughput.

| # | Grade | Finding |
|---|---|---|
| E1 | Reported (verifier-measured) | `app.py:2658-2677` — `_write_batch` calls `RichLog.write()` **once per line**, measured 605-669 µs each; a 50-line batch stalls the reader ~40 ms. One combined write measures 9.15 ms (**4.4x** better). **The finder's proposed mechanism was refuted**: the `max_lines` trim is only ~10% of the cost, so batch the write, do not tune `max_lines`. Caveat: a combined write measures one `render_width` for the block, so wrap behavior for mixed-width lines shifts slightly. |
| E2 | Reported | `app.py:1412-1418` — the session log is written and flushed **per line**, on the event loop, inside that same blocking round-trip. |
| E3 | Reported | `app.py:2669-2681` — each received line is ANSI-scanned three to four times. |
| E4 | Reported | `serial_port.py:388` — `SerialReader.process` re-scans the whole accumulated buffer per chunk, so a stream that never emits a terminator in the configured `eol_rx` mode is O(n²). Bounded in practice by `apply_backspace` for redraw-style devices. |

**Quantified context (Assessment):** at 115200 baud a 4096-byte chunk is ~44 ms
of main-thread work against ~355 ms of wire time — roughly 12% duty cycle. The
path becomes wire-limited only near ~900 kbaud sustained. E1-E3 are real but not
currently a correctness risk at typical baud rates.

## Invariants verified as holding

Recorded so a future pass does not re-litigate them.

- **`_dispatch_guard` cannot deadlock.** Both acquire sites use
  `blocking=False` (`app.py:2837, 2865`) with `finally` release. The main thread
  never parks on a lock a worker holds, so the classic cycle is unreachable.
  `RLock` is correct for nested `ctx.dispatch`; a plain `Lock` would self-deadlock.
- **RX batching is already well-tuned.** `on_lines` fires at most once per
  `port.read()`, self-adjusting to the 4096-byte ceiling under load — measured
  exactly 4096 bytes per call at every consumer speed, ~22 round-trips/s at
  921600 baud. `SerialReader` sustains 2.62 MB/s (28x realtime at 921600).
- **XMODEM/YMODEM never contend for the port.** `ctx.serial.io()` sets
  `serial_claimed`, which suppresses only the display path; the reader thread
  remains the sole `port.read()` caller and feeds `rx_queue`, which
  `QueueByteReader.getc` drains. No concurrent port read exists anywhere.
- **Every `call_from_thread` site is `try/except RuntimeError`-wrapped**, per the
  documented contract — all ~20 of them, checked individually.
- **Binary capture stays off the main thread entirely**: `SerialReader.process`
  feeds `CaptureEngine.feed_bytes` and returns no lines, so `/cap.bin` produces
  zero `call_from_thread` round-trips. `_flush_bin` batches at 4096 and never fsyncs.
- **No busy-waits on the reader path.** The `if not data: time.sleep(0.01)` is
  reached only after a `read()` that already blocked for `SERIAL_READ_TIMEOUT_S`.
- **`wait_for_match` closes its documented arrival gap**: the predicate is
  installed *before* the buffer scan (`repl.py:495-502`).
- **`/expect` does not double-consume serial data** — `feed_lines` is a passive
  tap called after display and logging, so a matched line still renders.
- **Script lifecycle uses `post_message`** (thread-safe via
  `loop.call_soon_threadsafe`), and every handler guards with `SHUTDOWN_RACE`.
- **All non-Textual threads are `daemon=True`** (CLI reader, MCP reader, MCP
  banner watcher, `open_with_system` launcher).
- **`replace_cfg`'s clear+update is safe** (finding raised and **refuted**): the
  reader's only hot-path cfg read is `.get("eol_rx", "auto")` with a default, so
  the momentary empty-dict window cannot raise there.
- **`_recent_lines`, `serial_claimed`, `_shutting_down`, `_line_counter`** and
  the `ctx.ns()` dicts are single-writer or GIL-atomic — not races.

## Coverage and honesty

41 unique findings were raised; 19 were adversarially verified (18 confirmed, 1
refuted). **22 remain Reported but unverified** and should be treated as leads,
not findings. The notable ones:

- `app.py:1291` — auto-reconnect may give up permanently if the connect
  following a successful probe fails (`_reconnecting` still True).
- `app.py:1266, 1281, 1283` — `_auto_reconnect`'s "main thread only" docstring;
  the reconnect worker surviving a manual connect and a config switch;
  `stop_event` overloaded for two purposes.
- `repl.py:779` — `feed_lines` returns on first predicate match, dropping the
  rest of the batch from the ring buffer.
- `repl.py:509` — a stale `_expect_event.set()` possibly satisfying the next
  `wait_for_match`.
- `repl.py:582-584` — non-atomic snapshot-then-clear of `_recent_lines`.
- `app.py:3154` — config/port-effect callbacks mutating widgets on the worker thread.
- `serial_engine.py:469` — trailing partial line dropped on disconnect.
- `terminal_host.py:704` — the help HTTP server is never shut down; its port
  latch is an unguarded check-then-set.

Two limits of this pass: no real hardware was attached, so all timing shapes are
synthetic; and `run_test()`-style Pilot coverage was not extended, so none of
these findings currently has a regression test.

## Suggested remediation order

1. **T1 + T2** together — identity-check the port in `finally` as the minimal
   fix, or (better) hold the reader worker handle and `join()` it in
   `disconnect()`. The design call is whether `on_lines` should stop blocking (D2).
2. **T4 + T5** — two unconditional `.set()` calls in `on_unmount`. Independent
   of everything else.
3. **T7 + T8 + T9** — bind-to-local, and widen the caught exception set. Same
   shape three times; retires root cause 1.
4. **T3 + T6** — per-operation cancellation tokens and a one-outermost-script
   guard; retires root cause 3.
5. **D1** — correct `CLAUDE.md` and the `repl.py` comment. Cheap, and it stops
   the next change from being reasoned out of a false model.
