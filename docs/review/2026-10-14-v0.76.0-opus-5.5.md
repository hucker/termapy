**Scope note:** the 2026-08-19 pass reviewed this code as a threading
mechanism (who owns the reader, how teardown joins, which thread touches a
widget). This pass asked a different question of the same code: does every
received byte reach every consumer that was promised it, once, and does
every sent byte leave through one path that reports failure? Chuck asked
for it because recent work might have left cruft or regressions in the
reader and the RX hand-off.

**Verdict:** the threading mechanics hold — the 08-19 fixes are intact.
The data semantics did not. **A second `/expect` passed instantly on the
first reply** (E1, reproduced: `True` in 0.000 s), **a match dropped the
lines that arrived with it** (E2, reproduced), and **a passive session kept
every byte it ever received** (R1, reproduced: 36,000 of 36,000 bytes held).
When the TUI fell behind it dropped lines from the session log, the text
capture and the expect buffer while saying only the display had lagged
(R2); MCP's `/cap.text` recorded nothing (R5); `/term.hex` showed decoded
text re-encoded rather than the wire bytes (H1); `/raw` had three
implementations with two behaviors (T1). Most of these date from March and
survived because earlier reviews were scoped by mechanism or module rather
than by data contract, and every test of these paths called the operation
once.

## Rules checked and holding

- `rx-never-blocks` — the `_rx_enqueue` wake-up latch and its event
  ordering.
- `reader-owned-by-engine` — join-based teardown, and port-close ownership
  by identity.

Also read and sound, with no registry row at the time: `SerialReader`
decoding and line splitting, `wait_for_idle`, `drain` purging the driver
buffer, and `CaptureEngine`'s locking.

## Suggested remediation order

- **A — correctness (E1-E3, R1-R5):** expect consumes through its match
  under one lock; a bounded `rx_queue`; every line to every consumer through
  one host method, with only the TUI's render capped; a last-resort guard
  in `read_loop`; a port-lost teardown shared by every frontend.
- **B — hex view (H1):** build the rows from the received bytes in
  `SerialReader`, for every frontend.
- **C — one TX path (T1, T2):** one `TerminalHost._serial_write`, one
  `/raw`; `/raw` sends no line ending (decided 2026-10-14).
- **D — cruft (M1, K1)** and this record.

Not chosen: a `docs/decisions.md` entry requiring a fix that drops data to
name every consumer of it; an `ast` guard against unbounded buffers. Not
scheduled: `try_reconnect`'s extra open and close (an extra DTR edge), and
the partial line dropped when a claim starts mid-line.

  cancelled meanwhile, closes it (`reconnect-opens-once`). **Partial line at

  arrived, dropping a prompt that came in under 200 ms before the claim; a
  binary capture, which returns before the claim check, glued it to the first
  line after the capture instead. Both now flush it first
  (`rx-every-line-delivered`). The hex-view test that pinned the discard
  (`test_a_claim_discards_the_pending_row`, from `fix/hex-view`) was rewritten
  to the new contract.
