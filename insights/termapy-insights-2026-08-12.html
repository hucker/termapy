03The patterns doing the heavy lifting

These are ranked by how much they changed the codebase, not by how often they appear.

Highest leverage

You convert a bug into an invariant

Three times in six days you refused to accept a fix for the thing you reported and demanded the rule behind it instead. Each refusal produced a systemic change and a permanent guardrail.

“THis is a very odd thing to miss can you enumerate for me each of the ‘standard aruments’ that termapy accepts? We should NEVER have this type of error.”after /term.color 2 silently toggled → became the whole settings-grammar rule
“Before working on these independently as a bunch of bolt-on fixes is there any unifying path on these?”on the security findings → became the capability sandbox instead of five patches
“It seems like EVERY place where we use files it should be relative to the folder that the .cfg file resides in with no allowance to go .. up the tree.”one path question → containment across every file-reading command

The tell is that all three are now enforced in code or in CLAUDE.md, not just fixed. This is the single most valuable thing in the transcript and it is entirely yours — in each case the proposed fix was narrower.

Most efficient

You paste the terminal instead of describing the bug

Seven bug reports were raw TUI output with no prose diagnosis — the /term.color toggle sequence, the 0-byte /cap.text capture, the port table's - column, the demo script's /print echo wall. Zero of those needed a clarifying round trip.

Compare the ones you described in prose: the REPL focus bug took four exchanges (“no longer allows keyboard input” → “runing from run menu does the same” → “when I type in /run welcome it hangs”) because the symptom shifted each time. The artifact is unambiguous; the description isn't.

Course correction

You attack the metric, not the code

The app.py arc is the best sequence in the six days. It starts with you rejecting a result:

“we did a major session adn we went from 3800 to 3500 which from my perspective is no change.”

Then refusing to continue until the goal is restated:

“Before we do something I need to ask what SHOULD we be doing. I have found that UI's with many pieces structurally must have a lot of code… Making it small is hard because the problem isn't small.”

Then finding the metric that actually pays:

“that is the sort of thing that ‘pays’ for me if I can test more things in the app monolith. My feear of course is that I add all these tests… BUT I increase the size of the app.py so I can't get ahead.”

Outcome: the size ratchet was built and then deleted (chore/remove-app-ratchet), replaced by a written principle that app.py health is testability and placement, not line count. You killed a treadmill mid-stride. The probe “if will mcgaughan wrote this how would it look different?” is a good instrument — a named practitioner as a lens gets a sharper answer than “is this good code?”

05What's worth changing

Your CLAUDE.md is already unusually mature — the settings grammar, the error-message vocabulary, the app.py principle, the count policy all got written down because of frictions in this window. That's the loop working. These are the gaps it doesn't cover yet.

AddBecause
Shell hygiene. “The Bash/PowerShell tools already start in the project root and the cwd persists. Never prefix a command with cd <repo>.” 712 of 791 Bash calls did exactly that.
Answer before acting. “For a design or 'should we' question, answer in prose first and stop. Do not read code, plan, or edit until asked.” Most of the 10 interrupts were implementation starting mid-decision.
Size budget on extractions. “An extraction must not be larger than what it replaced. State the before/after line count when proposing one; if it grew, cut it before showing it.” Raised twice, once about app.py and once about HistoryNavigator.
Checkpoint design arcs. “When a discussion settles a principle, write it to docs/ or CLAUDE.md in that turn — not at the end of the session.” Three context exhaustions; the app.py principle nearly didn't survive one.
Promote the merge gate into CLAUDE.md. The pause-for-manual-test rule currently lives only in auto-memory. It's the backbone of all 41 merges and it isn't written in the repo.

One habit worth adopting

You already paste terminal output as bug reports and it measurably outperforms describing them. Extend it to the case where it currently fails: TUI state bugs (focus, input, rendering) have no pasteable artifact, and those are exactly the ones that took four rounds. For those, lead with what you pressed and what didn't happen, in that order — the sequence is the artifact.
