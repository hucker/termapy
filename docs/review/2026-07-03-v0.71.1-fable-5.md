## Verdict

**Termapy is a real tool, not a toy — the engine is unusually well-built, but two Verified defects touch the exact surfaces it markets, and they should be fixed before it's pitched as "THE goto tool for serial debugging."**

The core is genuinely strong: 2,627 tests that mostly exercise real behavior (including real-serial loopback), a deterministic ~100-command CLI gold test, clean ruff/ty gates, a coherent three-frontend architecture (TUI/CLI/MCP over a shared host), a capability-gating security model that holds where it matters, and real hardware works exactly as advertised (full FTDI pedigree, byte-exact loopback, clean disconnect/reconnect). The port-pedigree subsystem is, as a bundle within a serial terminal, plausibly unmatched.

But:

- **Killer (Verified):** listing ports — and *every* connect, and the 2.5 s auto-reconnect loop — physically opens every *other* attached port and asserts DTR/RTS on it. On the most common dev boards (Arduino Uno/Nano, ESP32), that is a reset. The subsystem that is the selling point is invasive by default.
- **High (Verified):** `/expect` — a documented scripting primitive — is non-functional in CLI mode; scripts that use it hang to timeout in CLI while working in TUI/MCP.
- **High (Reported):** the MCP "destructive" confirmation gate is honor-system and bypassable; the real safety boundary is capability-gating, which does hold.
- **High (Verified):** the entire MCP subsystem (~181 tests, ~2,200 lines) is never executed by CI, tox, or the release gate — the green badge certifies nothing about it.

**Top 3 strengths:** real-I/O test discipline + deterministic gold test; the port-pedigree data model and resolution-transparency design; the capability-gating security model (7 gates verified solid by the security agent).

**Top 3 risks:** the invasive port probe (H1); CLI/MCP feature-parity gaps that ship silently (`/expect`); a coverage/CI story that overstates what's proven (MCP untested in CI; headline coverage 69% vs. honest 60%; the whole TUI layer untested).

**Differentiator claim ("likely unmatched"):** defensible in the qualified form *"unmatched as a combination, among serial terminals"*; **not** defensible in the absolute form (dedicated USB tools go deeper; Linux `tio` covers the common cases; and the pedigree is only as good as its facts, which contain errors — see below).

**Fit today:** suitable as a daily-driver interactive terminal and for MCP/LLM-driven device work by someone who understands the safety model. **Not yet** suitable as an unattended/multi-device bench tool (H1), nor for CLI automation that relies on `/expect`, nor to be sold on "unmatched" pedigree until the chip-DB errors and H1 are fixed.

## Killer issues

### K1 — Listing/connecting to a port opens every *other* attached port and asserts DTR/RTS (can reset dev boards). **Verified. Severity: High.**

**Chain (all read end-to-end, then reproduced):**
- `open_serial()` calls `resolve_port()` on every connect — `config.py:678`.
- `resolve_port()` → `_gather_all_chip_facts(connected_port)` with **`fast` defaulting to `False`** — `port_control.py:1000`, default at `:823`.
- `fast=False` → for every enumerated port, `_facts_from_port_info` runs `if not fast: facts.in_use = _check_in_use(...)` — `port_control.py:727-729`.
- `_check_in_use` opens `serial.Serial(port=device, ...)` without setting `dtr`/`rts` — `port_control.py:657-664`. Vendored pyserial defaults `_dtr_state=True`/`_rts_state=True` (`vendor/serial/serialutil.py:216-217`) and applies `DTR_CONTROL_ENABLE`/`RTS_CONTROL_ENABLE` on open (`vendor/serial/serialwin32.py:180,211`).

**Reproduction (orchestrator, safe recording fake — no real hardware touched):** a single `resolve_port("COM7", connected_port="")` opened **2** ports:
```
opened COM3  dtr=default(True)  rts=default(True)
opened COM7  dtr=default(True)  rts=default(True)
```
So connecting to COM7 also opens COM3 and asserts DTR/RTS on it. On a DTR-auto-reset board that is a reset. The `reconnect_loop` (`serial_engine.py:535-566`) repeats the full probe every 2.5 s indefinitely while waiting for an unplugged target — strobing DTR on every other board on the bench. `list_ports`/`--ports`/the port picker all probe too, yet never display the `in_use` result they paid for (only `--ports --json` uses it). The picker path is additionally O(N²) on the Textual main thread (`dialogs/_common.py:53`).

**Consequence is board-dependent** (only boards wired for DTR/RTS-triggered reset — Arduino Uno/Nano, ESP32 — reset; FTDI cables, many industrial devices, do not). It is disruption, not damage. But "merely listing ports can reboot my board" is precisely the failure a skeptical embedded engineer will hit and remember.

**The fast path already exists** — only `--watch` uses it (`cli_flags.py:356`). Fix shape: resolution needs only identity fields, so use `fast=True`; give table/picker a middle tier (extras, no probe); make the destructive probe opt-in; and pre-set `dtr=False`/`rts=False` before open where the platform allows.

## Findings by dimension

### Port subsystem (finder: Fable 5; H1 = K1 above)

- **R2607-01 — High — Verified — K1** (above).
- **R2607-02 — High — Verified — `/port.connect` reports success unconditionally.** `_handler_connect` ignores the boolean from `ctx.serial.connect()` and returns `ok` — `builtins/commands/port.py:96-97`. A failed open *and* the "Already connected" refusal both yield `ok`, so scripts / `$(VAR) <-` capture / MCP `run_command` see success on failure. Baseline confirmed: `/port.connect COM99` while connected → "Already connected", the requested port silently dropped, and baud/mode applied to cfg *before* the refusal (`port.py:75-95`) so the title bar can disagree with the live port.
- **R2607-03 — Medium — Reported — `/port.chip.*` breaks under the doc-recommended SN config.** `chip_info`/`chip_field` match literal device names only, never resolving an SN/fallback spec (`port_control.py:1128-1134,1169-1174`), while `port_info` resolves correctly (`:1213`). A user who follows `help/ports.md` (`"port":"A1B2C3D4"`) and types `/port.chip` gets "No port matching".
- **R2607-04 — Medium — Reported — chip-DB pedigree errors (web-checked by agent).** `(0x0403,0x6010)` → "FT2232C/D/H, high-speed, 12 Mbaud" (`usb/chips.py:53`) but FT2232D is full-speed (needs `bcdDevice` to disambiguate). `(0x16C0,0x0483)` → "Teensy 2.x, full, 2 Mbaud" (`usb/chips.py:132`) but that PID is used by all Teensy incl. 4.x (high-speed). `USB_VENDORS[0x16C0]="Teensy"` (`usb/vendors.py:57`) shadows the canonical "Van Ooijen Technische Informatica" that the bundled full table already has. Native-CDC `max_baud` values (STM32 VCP, Pico, Leonardo) are invented precision — there's no UART.
- **R2607-05 — Medium — Reported — `--watch` in-use / open-close events are dead code.** Fast gather leaves `in_use=None`, so the transition diff (`cli_flags.py:469-472`) can never fire; yet `entry.py:173-174` and the module docstring advertise in-use change events. A test pins the always-`-` behavior (`tests/test_cli_improvements.py:556-567`).
- **R2607-06 — Medium — Reported — in-use detection is only correct on Windows.** The probe omits `exclusive=True`; POSIX exclusivity is advisory `flock` (`vendor/serial/serialposix.py:381-389`), so opening a port already held by picocom/tio succeeds → "no" for a busy port. `help/ports.md:135-151` presents in-use as cross-platform fact.
- **R2607-07 — Medium — Reported — numeric serial numbers are unreachable via `/port.connect`.** `parse_open_args("0001")` → `(port=None, baud=1)` (`port_control.py:130-147`); the all-digit clone SN in ports.md's own example connects the current port at baud 1.
- **R2607-08 — Low — Reported — cluster:** `/port.info` prints a latency-timer hint on a value it can't read (`port_control.py:1269` vs. guarded `:1064-1076`); `DEMO_VT100` missing from `_RESERVED_PORTS` (`:926`); resolution candidates not `.strip()`ed (`:1001-1005`); several stale ports.md claims (chip table location, SN "rightmost column", picker "Max baud column").

### Frontend parity & core logic (orchestrator + partial Fable)

- **R2607-09 — High — Verified — `/expect` is non-functional in CLI mode.** CLI's reader callback `on_lines` only displays (`self._raw(line)`) and never calls `self.repl.feed_lines()` — `cli.py:658-662` — whereas TUI (`app.py:2781`) and MCP (`mcp/server.py:304`) both feed it. `/expect` matches via `feed_lines` (`repl.py:257,400`), so in CLI the predicate is installed but no RX line ever reaches it. **Reproduced on COM7 loopback:** `/expect timeout=3s match=HELLO_EXPECT` timed out after the full 3 s even though `HELLO_EXPECT_2607` was echoed back immediately before. Impact: any `.run` automation using `/expect` hangs in CLI but works in TUI/MCP — a silent parity gap in the scripting layer.
- **R2607-10 — Low — Verified — `/sleep` is referenced but doesn't exist.** No `sleep` command is registered; the real command is `/delay` (`app_hooks.py:407`, `cli.py:302`, `repl.py:1535`). `README.md:466` ships an "Init" custom-button whose command is `...\n/sleep 500ms\n...` — it would error on click — and `defaults.py:521`'s script template comment shows `/sleep` too.
- **R2607-11 — Low/Info — Verified — behavior seeds from baseline:** one-shot `-e` returns exit 0 after a failed `auto_connect`; unknown command via `-e` correctly exits 1. Exit-code semantics for connect failures are under-specified (and the gold test can't catch it — see R2607-15).

### Security & capability posture (finder: Fable 5)

- **R2607-12 — High — Verified (bypass path) / Reported (full claim) — the MCP "destructive" confirmation gate is honor-system and bypassable.** The `confirm` flag is an LLM-set tool parameter (`mcp/server.py:784`); the gate `if safety=="destructive" and not confirm` lives only inside `_dispatch_via_profile` (`:993`), which **returns `None` for any slash command** (`:942-943`, orchestrator-confirmed). `/term.send <bytes>` is a builtin with no `needs=` gate (`term.py:446-466`), so raw wire access never touches the safety tier. Actor: LLM via MCP. The capability gate is the real boundary and it holds; the destructive/confirm tier is advisory.
- **R2607-13 — Medium — Reported — capture write-path has no containment.** `_resolve_path` uses an absolute filename verbatim and joins+resolves a relative one with no `is_relative_to(cap_dir)` guard (`builtins/commands/cap.py:83-88`); reachable by MCP when connected. The MCP capture *read* resource *is* traversal-guarded (`mcp/server.py:843-846`) — an asymmetry.
- **R2607-14 — Low — Reported — residual env-into-wire via `on_connect_cmd`.** `expand_env_cfg` expands `$(env.X)` in every cfg string incl. `on_connect_cmd`, dispatched on connect (`config.py:597`; `mcp/server.py:517`). Author-controlled, but re-creates the prior `$(env.PATH)` incident class.
- **Verified-solid gates (positive):** env expansion is repl-only, never reaching the wire for bare device commands (`env.py:179-183` vs. `var.py:492-497`); `/os` is double-gated (env flag + `needs=interactive`, rejected for MCP); help HTTP server is `127.0.0.1:0` ephemeral; MCP does **not** execute filesystem plugins (only TUI does, a documented trust boundary); `update_check` is a bounded, PII-free 7-day pypi poll.

## The differentiator claim

Claim: realtime port feedback + pedigree identification "likely unmatched in other tools."

**Holds, qualified:** as a *bundle inside a serial terminal*, nothing found matches it — mainstream terminals (PuTTY, Tera Term, RealTerm, CoolTerm, Docklight, HTerm) offer at most a friendly-name list; `docs/comparison.md` has no port-pedigree row at all, and (post-fix) it's the most defensible row missing from the public table.

**Needs qualification (Assessment):**
1. Linux `tio --list` covers the common 70% (device/driver/`by-id`, and its Topology ID works for SN-less clones — which termapy's SN grammar cannot connect by; a real gap).
2. Absolute "unmatched pedigree" is false — USBTreeView/USBDeview and `udevadm`/`lsusb -v` go deeper (bcdDevice, power, hub chain).
3. The pedigree is only as good as its facts — R2607-04's errors are exactly what a skeptic spot-checks first.
4. "Realtime" currently trades against "non-invasive" (K1): the realtime paths that probe can reset the boards being inspected.

**Verdict:** *"unmatched as a combination, among serial terminals"* is a claim termapy can stand behind and should put in `docs/comparison.md`. The absolute form is not defensible. The two things that most threaten even the qualified claim — the chip-DB errors (R2607-04) and the invasive probe (K1) — are both fixable in-repo.

- **R2607-12 (MCP destructive gate) — REVIEWED, by design** (branch
  `chore/mcp-confirm-language`; comment softened, no behaviour change).
  The finding is technically true (the `confirm` flag is honor-system and
  raw `/term.send` bypasses the gate) but judges it against a security goal
  termapy deliberately does not have.  The gate is a *best-effort
  confirmation courtesy* for cooperating clients, not a boundary -- and it
  shouldn't be one: termapy is a bridge, and knowing which commands are
  destructive is the **device's** responsibility (declared per-device in
  the profile), not the bridge's.  Building device-safety policy into the
  bridge would also couple it to anticipated devices and work *against* the
  goal of talking to arbitrary devices.  Action taken: softened the code
  comment that overclaimed "MUST require human-in-the-loop approval" so it
  no longer promises a boundary it isn't.  **Roadmap (not built now, no
  device forces it yet):** a two-axis safety/hazard *declaration*
  vocabulary in the profile schema, and real MCP `elicitation/create` to
  replace the honor-system marker -- both device-agnostic mechanisms,
  added when a real hazardous device (motor / billing / radio) or an
  elicitation-capable client justifies them.

- **R2607-13 (capture write-path containment) — REVIEWED, by design** (no
  code change).  `_resolve_path`'s model is the ordinary filesystem
  convention -- a relative filename resolves under the config's `cap/`
  dir, an absolute path is absolute -- and a human who types an absolute
  capture path *means* to write there; that's a feature, not traversal.
  The only real concern is an untrusted caller (an LLM via MCP), and per
  the same reasoning as R2607-12, termapy is a bridge, not a filesystem
  sandbox: `termapy --mcp` runs with the user's own permissions and the
  MCP client / OS owns that scope.  The MCP read guard
  (`capture_resource`) scopes a *resource* (capture files live in `cap/`),
  it is not a general sandbox; writes go where the command says.  The
  read/write asymmetry is therefore coherent, and adding a write sandbox
  would push the bridge toward being a boundary we've deliberately
  declined to be.  (If a future need arises, the surgical option is to
  confine only the MCP write path -- left as a note, not built.)
