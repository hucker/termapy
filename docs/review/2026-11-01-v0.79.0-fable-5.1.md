# Config subsystem review -- 2026-11-01

**Version:** 0.79.0, `main` at `7748df52`; read on `feat/cfg-architecture` at `dace95fa`
with the `cfg=` declaration commit still uncommitted.
**Host:** Windows 11, no hardware.
**Reviewer:** Claude Fable 5.1, solo. The per-command key inventory it cites came from one
agent earlier the same day, every row carrying a file:line, spot-checked by the reviewer.
**Scope:** asked for by Chuck as "review the architecture of the cfg file system in general
and critique the capabilities and lack of capabilities". A design read of `defaults.py`,
`config.py` (resolution, creation, the writer, the migration write-back, env expansion,
validation, load), `migration.py`, `folders.py`, `app_dirs.py`, `dialogs/config_editor.py`,
`builtins/commands/cfg.py`, `pickers.on_config_result` and
`terminal_host._apply_port_effects`.
**Complete:** partial by design: the architecture and its capabilities, not a defect hunt over
every reader of a key (the day's inventory covered the plugin folders; the serial, MCP and
script consumers were read only where a finding led there).
**Verification stage:** every claim graded. Two reproduced in the CLI (the `/help` pages, the
editor's variable message); the rest are exact-path reads.

## Verdict

The storage model is strong and better guarded than most of the codebase: one folder per
config that travels with the project, data folders from one table that exist while something
is in them, one writer in one order, one creator, one deleter, one renamer that carries every
sidecar, a 34-step migration chain with retired-key explanations and from-the-future detection,
environment templates read with the one boolean vocabulary, and a settings editor with per-key
help, live validation, find, and now the commands that use a key.

What is weak is the *schema*. What a key is, what values it takes, when it takes effect and who
reads it is spread over five places in three vocabularies, so the three validators disagree, no
surface can say "takes effect at reconnect", and three keys quietly do nothing after startup.
Two capabilities a daily driver reaches for are missing: keeping a session change without
opening the editor, and a settings layer shared by many configs. There is one data-loss path: a
config is rewritten in place at load with no backup and no atomic write.

4 High, 4 major, 5 minor. The first three Highs are what this branch's plan is already
executing (one reader, one table, one validator); the fourth is a ten-line fix.

## The model as it stands

- **Where configs live.** `config.cfg_dir` resolves `--cfg-dir`, then `TERMAPY_CFG_DIR`, then
  `./termapy_cfg` if present, then the OS default; the first two must exist, the last is
  created by the first write. Each config is `<root>/<name>/<name>.cfg` with stem-named
  sidecars (`folders.SIDECARS`: history, log, report, profile, symbols) and the data folders of
  `folders.FOLDERS`, created at a write and pruned when empty. A global layer at the root holds
  `plugin/`, `dev/` and `lib/`; the per-config folder wins a name clash. App-wide state (update
  checks, running breadcrumbs) is `app_dirs.app_state_dir`; an app-wide `config.json` is
  reserved and nothing reads it.
- **The file.** Flat JSON in `DEFAULT_CFG`'s order through the one writer
  `config.write_config_file`; `config.new_config` builds and `create_config` writes a new one
  (wizard, `--new`, `/cfg.new`, Save As); `delete_config` and `rename_config` are the only
  removal and rename. `config_version` drives `migration.MIGRATIONS` (34 steps) with
  `DEPRECATED_CFG` naming why a retired key went; a file from a newer termapy gets one upgrade
  hint. `load_config` migrates, backfills missing keys one level deep, writes the file back
  when anything changed, expands `$(env.NAME|fallback)` (booleans through `parse_bool`, the
  on-connect fields excluded), then `validate_config` returns warnings.
- **The session.** The loaded dict is the session. `/cfg key value` and `/cfg.auto` coerce to
  the current value's type and check a fixed-value set, then `apply_cfg`; every `/term.*` and
  `/port.*` setter does the same through `apply_cfg` or a `cfg_update` effect. Nothing writes
  the file but the editor's Save. `$(CFG)` and the other session variables are expanded by the
  variables engine when a value is used (`echo_fmt`, `cli_prompt`).
- **Surfaces.** The TUI editor shows the file's text (templates visible) with per-key help,
  valid values, the value's status, a preview, find, and the commands that declared the key;
  `/cfg.dump`, `/cfg.info`, `/show.cfg`, `/cfg.list`, `.load`, `.new`, `.delete`, `.rename`,
  `.icon`, `.file`, `.explore`; `termapy --new`, `--demo`, `--check`; `/help <key>` and the
  CONFIG section of a command's page; the MCP catalog carries each command's `cfg`.
- **Where the knowledge is.** `DEFAULT_CFG` (defaults and types), `CFG_HELP` (prose, valid
  hint, preview), `CFG_CHOICES`, `MANAGED_CFG_KEYS`, `BOOL_CFG_PATHS` (derived), the editor's
  `_INT_KEYS` and `_STANDARD_BAUDS`, `validate_config`'s hand-typed checks, `help/config.md`'s
  table (defaults generated, descriptions by hand), `builtins/demo/demo.cfg` kept in step by a
  test, and since this branch `Command.cfg`.

## Findings

### H1 -- The schema lives in five places with three vocabularies, and they disagree (High, Verified)

`DEFAULT_CFG` carries the types, `CFG_HELP` the prose and a hand-written valid hint,
`CFG_CHOICES` the enumerations, the editor its own `_INT_KEYS` and `_STANDARD_BAUDS`
(`config_editor.py:206-222`), `validate_config` its own `_check_set` / `_check_positive`
calls (`config.py:953-1097`), and about 148 read sites restate a default in a literal, five of
them differently from the table (`echo_fmt` `repl.py`, `cli_prompt` `cli.py`,
`request_err_pattern` `repl.py`, `border_color` `app.py`, a literal `/` prefix in
`mcp/server.py`). The editor's baud set lacks 110, 600, 14400 and 28800, which
`STANDARD_BAUD_RATES` has, so four standard rates show yellow in the editor and pass at load.
Consequence: "is this value OK" has three answers depending on where you ask. Fix: the branch
plan's commits 4 and 5 (one reader with the table's default; one `CfgKey` table that
`DEFAULT_CFG`, `CFG_HELP`, `CFG_CHOICES` and the editor's sets derive from, and one validator
behind the file, the editor and `/cfg`).

### H2 -- Validation never refuses, and each surface checks a different subset (High, Verified)

`validate_config` returns warnings; a config with `max_lines: 0` loads. `/cfg` and `/cfg.auto`
coerce to the existing value's type and check `CFG_CHOICES` (`cfg.py:109-120`), nothing more:
`max_lines 0`, `encoding nope` and `config_version 99` are accepted. `max_grep_lines`,
`proto_frame_gap_ms` and `default_response_timeout_ms`, whose help says "Positive integer",
are checked nowhere; an uncompilable `request_err_pattern` fails at first use. Over MCP a bad
`/cfg.auto` is silent until the feature misbehaves, the opposite of what an agent doing
bring-up unattended needs. Fix: the one validator of H1, with `/cfg` refusing
(`Invalid <key>: <value> (<reason>)`), and load warning on the range keys.

### H3 -- Three keys lie about when they take effect, and the schema has no word for it (High, Verified; the connect-time pair Reported)

`echo`, `hex` and `line_no` only seed session flags at host start
(`terminal_host.py:639-648`); `/cfg echo on` changes the dict and nothing visible, while
`/term.echo` changes the flag and not the dict. `encoding` and `eol_markers` are captured into
the reader at connect (`serial_engine.py:484-491`, reported by the inventory, not re-read), so
`/term.encoding` changes what is sent but not how received bytes decode until a reconnect.
`auto_connect` is honored by the TUI only (`cli.py:671`, `mcp/server.py:1458`, reported).
Nothing in the schema says whether a key is live, read at connect, or read at start, so neither
the help nor the editor can. Fix: an `applies` field on the schema record (`live`, `connect`,
`start`), rendered on the key page and the editor's help line; make the three seed-only keys
live by routing `/cfg <key>` through the flag, or declare them `start` and say so.

### H4 -- A load rewrites the file in place, with no backup and no atomic write (High, Verified)

`load_config` writes the migrated and backfilled config back (`config.py:1288`) through
`write_config_file`, which opens the file for writing and dumps into it (`config.py:451-452`).
A crash between the truncate and the dump leaves an empty `.cfg`; a migration bug ships to every
config on the first launch of a new version with no way back; `config.py` has no `os.replace`,
no temp file and no `.bak`. Fix: write to `<name>.cfg.tmp` and `os.replace`; on a migration
keep `<name>.v<old>.cfg.bak` beside it, pruned at the next clean load. Ten lines, and the only
data-loss path this subsystem has.

### M1 -- A session change has no save path short of the editor (major, Verified)

`/cfg`, `/cfg.auto`, every `/term.*` and `/port.*` setter change memory only; the one persist
is opening the editor and pressing Save, which is TUI-only (`/cfg.edit` opens the system
editor in the CLI, and MCP has no file write at all, by sandbox design). TeraTerm has "Save
setup"; termapy has none, and an agent that turned `request_mode` on cannot keep it. Fix:
`/cfg.save {key}`, writing the session value of one key or all of them through
`write_config_file` after the same confirmation `/cfg` uses, refusing a key whose file value is
a `$(env.X)` template (the session holds the expansion, and the template must survive),
`safety="mutable"` so MCP asks. This also retires the per-setter "persist" question for good.

### M2 -- The editor's Save discards unsaved session changes (major, Verified)

The editor shows the file (`_disk_cfg`, `config_editor.py:108-115`), so a value set by
`/term.eol lf` an hour ago is not in the text; Save hands the edited file to
`app._switch_config` (`pickers.py:75`), which replaces the session wholesale. The user never
saw the session value and never chose to lose it. Fix: with M1 in place, the editor can open
with a one-line notice listing session values that differ from the file, offering
`/cfg.save`; without it, Save should at least re-apply the session's differing keys and say so.

### M3 -- No settings layer shared by many configs (major, Assessment on a Verified model)

`new_config` copies every default into every config (`config.py:331`), so ten boards are ten
copies of `max_lines`, the button layout, the colors and the prompt; a preference change is ten
edits, and the global layer at the root holds only `plugin/`, `dev/` and `lib/`. The reserved
app-wide `config.json` (`app_dirs.py:14-17`) is the natural home and has sat unused. Fix: a
`defaults.cfg` at the cfg root (per project) and `config.json` in `app_config_dir` (per user),
layered under each config at load, lowest first; `/cfg.dump --effective` shows the merge, the
editor stays the file's text and names inherited keys dim. The design cost is the editor's
"effective versus file" view; the load merge is small. This is the largest missing capability.

### M4 -- JSON with no schema: no comments, and nothing an external editor or an agent can validate against (major, Assessment)

A `.cfg` cannot carry a comment, and `\r` must be typed as `\\r`; the in-app editor's help
line compensates, VS Code gets nothing. An MCP agent learns the keys only from `/cfg.dump`'s
values, so a `/cfg.auto` is guesswork about type and range. Keep JSON (agents and tooling
read it) and generate a JSON Schema from the one table of H1: `termapy --schema` and
`/cfg.schema` for the catalog, and a `"$schema"` line in a new config so VS Code validates and
completes. The table makes this a one-function addition.

### m1 -- `DEPRECATED_CFG` stops at v25 while the chain is at v35 (minor, Verified)

`migration.py:37-85` ends with v25; the v22 nesting (a flat `port` or `baud_rate` typed back
in) and the v27-29 renames (`show_line_endings`, `echo_input`) get "unknown key (typo?)"
instead of the rename. Fix: extend the table, or better, have each migration step record the
renames it makes and derive the table.

### m2 -- Keys nothing reads (minor, Verified; parked 2026-11-01)

`show_traceback`, `ndjson_field_routing` and its three leaves are read by nothing; `protocol`
is display-only. The new `cfg-declared` guard catches reads without declarations, not keys
without readers; the "every key has a reader" guard waits on the delete-or-wire decision.

### m3 -- Custom buttons have no schema (minor, Assessment)

`custom_buttons` is a list of `enabled` / `name` / `command` / `tooltip` dicts validated
only by the editor's `enabled` special case; a `command` is never checked for a prefix or an
existing command, and no count is stated. The one table should give the list an item schema.

### m4 -- `config_read_only` is a picker flag, not a guard (minor, Verified)

It greys Edit, Rename and Delete in the pickers (`app.py:2171-2206`) and nothing else:
`/cfg.edit` from the palette, Save, `/cfg` and `/cfg.auto` all still work, as `CFG_HELP` half
admits. Either make Save refuse under it or rename it to what it does (`pickers_read_only`).

### m5 -- `./termapy_cfg` in the working directory wins silently (minor, Assessment)

Step 3 of `cfg_dir` picks up any `termapy_cfg/` in the cwd, so a stale one in a project
outranks the OS default without a word; `--cfg-dir` must already exist. Recorded already as
the quick-session design point; noted here so the resolution chain is listed with its
surprise.

## What I would do, in order

1. Commits 4 and 5 of the branch plan: one reader, one table, one validator (H1, H2), and
   from the table a JSON Schema (`--schema`, `/cfg.schema`, `"$schema"` in new files) (M4).
2. Atomic write and a migration backup (H4). Ten lines.
3. `/cfg.save {key}` (M1), then the editor's notice about differing session values (M2).
4. `applies` on the schema record and the seed-only keys made live (H3).
5. A shared settings layer (M3): design the editor's effective-versus-file view first; the
   load merge is the easy half.
6. Derive `DEPRECATED_CFG` from the migration steps (m1); a button item schema (m3); decide
   `config_read_only` (m4).

## Rules checked and holding

`cfg-written-in-order` (one writer, read), `config-created-once`, `config-deleted-once`,
`folders-ensure-only` (`_write_migration_run_files` goes through `ensure_folder`),
`reads-never-write` (`load_config`'s write-back is a load, the documented exception),
`sidecars-listed-once`, `bool-one-vocabulary` (`expand_env_cfg` reads a templated boolean with
`parse_bool`), `cfg-declared` (new on this branch). `writes-in-cfg-folder` was not re-read.
